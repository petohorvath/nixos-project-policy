# Maintenance

## Records

The current [legacy project records](https://github.com/petohorvath/nixos-project-policy/blob/main/policy/projects.json) preserve the adoption state, selections, and settings required by supported older checkers. Prepared v0.4.0 members select their release and settings in the existing policy caller. The current [pin records](https://github.com/petohorvath/nixos-project-policy/blob/main/policy/pins.json) identify shared pins, candidates, and rollout state. The [enrolled-member roster](https://github.com/petohorvath/nixos-project-policy/blob/main/policy/members.json) contains active repository identities only. The [support record](https://github.com/petohorvath/nixos-project-policy/blob/main/policy/support.json) records explicit retirement decisions and migration periods. All current records live on `main`. The selected policy release supplies the rules and checker code, including [development requirements](../policy/requirements.json). Keep approval and validation evidence on the corresponding PRs and CI runs.

For v0.4.0, declare `required_architectures` in the member caller as a nonempty JSON list encoded as a string. Optional `vm_targets` and `additional_required_checks` default to `[]`. Use `ci PATH --project NAME` with the selected checker to derive ordinary jobs, both compatibility channels on every required architecture, VM applicability, and the complete required gate set. Review any reduction in coverage explicitly, verify the observed statuses, and coordinate separately authorized merge-setting changes. Older releases retain their central settings and checker contracts.

## Pin candidates and approval

Routine shared-pin updates use one central PR. The PR adds a new batch containing an exact stable/unstable pair and every enrolled member's exact clean revision, and proposes that pair in `approved`. For a root-only update with no remaining member rollout, propose the new batch as `complete` and record the current approved pair in `previous`. Retain earlier completed batches. This allows the next routine PR to repeat the process without a separate completion change. A baseline batch that is already approved or historical cannot be reused as a candidate.

The prepared `Central pin proposal` workflow evaluates proposed records as unapproved data and reports `Pin batch / Complete candidate` on the exact PR head. Its trusted target workflow, coordinator, and baseline must come from the same current default-branch commit. Enrollment, support, and retained legacy settings come from that baseline; selected published immutable member checkers and declarations define coverage. A temporary candidate view retains the old approved pair. The workflow runs the complete enrolled batch and independently verifies GitHub jobs and artifacts for the exact attempt. Proposed code and checking requirements never execute. Normal member CI continues reading the old approval from `main` until the human-reviewed merge.

Prepare and review a routine update in this order:

1. Select the weekly artifact or prepare an urgent exact pair. Generated artifacts remain unapproved proposals.
2. Capture clean commits from the trusted roster and register those exact revisions in the batch. Keep integration projects at their intended committed dependency sets. Resolve real source or pin-bound lock failures through separately reviewed member PRs when needed.
3. Commit `policy/pins.json`, including the future approved pair and terminal routine batch, in one central PR. Keep enrollment, support, legacy settings, policy versions, and checker changes separate. Proposed records must be regular files committed at that exact revision; symlinks and uncommitted record edits fail.
4. Review the gate's head and baseline, member outcomes, every native system, both compatibility channels, ordinary checks, applicable VM tests, additional gates, and integration agreement plus behavioral execution. Retain the plan, native artifacts, GitHub provenance, and complete summary with the PR.
5. Obtain human merge approval with current complete evidence. The merge makes the pair authoritative for subsequent snapshots; candidate checks never write approval or member sources.

The `Complete candidate batch` manual workflow remains available for whole-batch investigation, and `Candidate member validation` for one-member investigation. Run them from trusted `main` with an exact committed proposal and batch ID. Their workflow-job results do not replace the PR gate. Follow the [complete-batch CLI procedure](checker.md#complete-enrolled-batches) for local execution and replay.

Preserve the captured plan and all worker artifact directories, including failed workers. Revalidate every required member, architecture, channel, and applicable gate when either candidate revision changes. Renew evidence after member source, settings, integration lock, enrollment, checker, or support changes; the coordinator requires a new attempt when its captured subjects or records change. A failed capture or worker must remain visible in the complete summary. Use integration-root checks and agreement at the consumed commits, even when separate member heads have already passed. Member source-fix or lock PRs, their exact tested revisions, and rollout or recovery records remain required where those contracts need them.

The maintenance workflow prepares an unapproved candidate artifact weekly. Manual urgent preparation accepts both `stable_revision` and `unstable_revision` as exact commits; supplying only one fails. With neither input, it resolves the configured stable branch and unstable once. Preparation creates no PR and needs no cross-repository write identity. Daily drift jobs inspect enrolled checkouts and configured merge gates.

For a selected candidate, create a batch record against exact clean project commits. Members selecting v0.2.0 or later can retain their chosen root lock and test the candidate through the policy runner. Older-policy members still need member lockfile PRs against the same pair. Include independently locked examples and other scopes that retain shared-pin requirements, preserve `follows` relationships, and reject unrelated lock changes. A stable release upgrade also changes relevant shared-channel branch declarations.

Use a targeted `nix flake lock` operation with exact candidate overrides on the owning inputs. Resolve `follows` before choosing override paths. Compare the resulting lock graph with its previous state: the intended revisions must be persisted, branch declarations and sharing must remain correct, and unrelated dependencies must be unchanged. For lockfile updates, build and check with `--no-update-lock-file` and no overrides to validate committed selections. Migrated members additionally run policy-owned compatibility checks with exact overrides; those runs intentionally use an effective graph different from the committed lock. Test these properties on controlled fixtures when changing update automation.

Record each exact tested member revision, required results, and approval evidence in the central PR. Candidate compatibility verifies effective root pins and executes full checks; the separate default check uses committed locks. Modern root-only members keep their lockfiles, policy versions, caller references, and source commits throughout a routine update. When source fixes, older contracts, or other lock scopes require member merges, preserve their separate human review and rollout records. Use `approved`, `rolling`, or `paused` while rollout remains active, and complete it after convergence. State-only pause, resume, completion, or withdrawal changes retain ordinary review without requiring a fictitious new candidate.

A pin update changes current records and requires renewed compatibility evidence. Migrated members need not change their selected root locks; older-policy members and other checked lock scopes may require lockfile updates. Keep `VERSION`, retained legacy selections, and member workflow references unchanged. At completion all enrolled members must satisfy their release's requirements against the new shared pins: compatibility coverage for migrated root selections, and approved locks where still required. Old policy releases do not grant continued access to old shared pins. During approved, rolling, or paused batches, compatibility runs target the central approved pair, never an arbitrary old/new allowance. Pausing still prevents further update merges.

The maintenance workflow emits candidate artifacts. Cross-repository PR creation requires a separately reviewed write identity and targeted-lock tests. Candidate generation does not approve batches or authorize member merges.

## Renewing PR evidence

A changed proposal head, pair, registered member revision, integration dependency set, or checking authority requires renewed validation. Exact registrations remain the subjects when an unrelated member branch advances; the coordinator never silently replaces them with new heads. Replay reproduces captured snapshots and cannot establish current merge eligibility by itself.

The reporter rechecks current GitHub proposal/base/run identities and support for every selected root and consumed integration member before reporting. Maintenance runs on pushes to `main`, the existing schedules, and manual dispatch. It invalidates open proposal checks whose baseline changed or selected release retired, recording why renewed evidence is needed. After a baseline change, update/rebase the proposal or reopen the PR to start a fresh target workflow event. Rerunning an older target workflow cannot attest a newer baseline; an ordinary rerun is suitable only while its original workflow and baseline remain current.

Activation must separately verify that `pull_request_target` is allowed by the repository's Actions event policy, that `Pin batch / Complete candidate` appears on the reviewed head, and that merge protection requires the intended trusted workflow/issuer and current-base validation. Status names alone do not establish workflow provenance. Native workers have read-only repository permissions; only isolated capture/reporting and invalidation jobs receive policy-repository Checks write. No cross-repository write credential is added. GitHub's [target-trigger security guidance](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target) describes its event-policy and execution constraints.

Final API checks and periodic invalidation are not atomic with a later merge. Up-to-date branch enforcement or equivalent merge-time revalidation, current support assessment, and human review remain activation responsibilities. A pending/failed inspection, unavailable artifact, or missing worker cannot authorize approval. Local workflow fixtures do not prove native ARM execution, hosted permissions, exact-head association, or live merge blocking. This repository change does not activate those settings.

## Audit access

Before enrolling the first member, configure the policy repository's `MEMBER_AUDIT_TOKEN` Actions secret with a fine-grained personal access token restricted to the enrolled member repositories. Grant only Administration read, Contents read, and Metadata read. Administration read permits [classic branch-protection inspection](https://docs.github.com/en/rest/branches/branch-protection#get-branch-protection); Contents read permits [branch metadata inspection](https://docs.github.com/en/rest/branches/branches#get-a-branch); Metadata read permits [active branch-rule inspection](https://docs.github.com/en/rest/repos/rules#get-rules-for-a-branch). Add newly enrolled repositories to the token's selection and renew it before expiry. No write permission is needed.

The maintenance audit passes that secret as `GH_TOKEN`; it does not fall back to the workflow's automatic token. The automatic [`GITHUB_TOKEN`](https://docs.github.com/en/actions/concepts/security/github_token) is limited to the policy repository. For a local audit, supply a credential with the same member access through `GH_TOKEN` or `GITHUB_TOKEN`; `GH_TOKEN` takes precedence. A GitHub App installation token with the same read permissions can also be supplied locally; hosted token issuance would need separate workflow setup.

With an empty enrolled-member roster, the audit needs no member credential and performs no member requests. Once the roster contains a member, a missing or inaccessible credential fails the audit with an inspection error. The JSON artifact identifies unknown settings separately from verified missing gates; do not interpret an HTTP 404 as absent protection. Verify hosted access before activation.

## Recovery

Pause further update merges when a regression appears. Keep the new pair when the repair is understood and testable, add a regression test, and validate the revised rollout before resuming. Roll back through tested PRs when impact is unacceptable or the repair is uncertain. A prior pair must still pass against current code. Either path needs human merge approval and tracked temporary differences; historical releases remain unchanged.

If a repair needs another nixpkgs commit, treat that pair as a revised candidate and rerun all affected project checks. Mark the batch complete only when adoption has converged; withdraw superseded candidates explicitly.

## Enrollment

Select a member explicitly before preparing its migration. Give it the agreed shell, tools, formatting, documentation, selected dependency, and checks. Resolve lint findings and preserve public contracts and specialized requirements. A draft may prepare an unpublished release; hosted checks require that published immutable release before activation.

For v0.4.0, use the selected release's caller template with matching workflow reference, `policy_version`, and documentation links. Declare architectures, VM targets, and additional required checks in the caller. Run `nix run .# -- --policy-root . check PATH --project NAME --shell` from a trusted current records checkout, then ordinary committed-lock tests, both compatibility channels on every declared architecture, and applicable VM suites. These operations work before enrollment and do not modify membership or approval records.

Generate the expected names with `ci PATH --project NAME`, inspect actual statuses on the reviewable member PR, and verify GitHub merge gates and audit access. Preserve that evidence on the PR. Add the repository identity to `policy/members.json` through a reviewed central PR only after this verification. Removal also requires a reviewed central PR. Enrollment plans belong in issues; ordinary upgrades and passing pre-enrollment checks leave the roster unchanged. The policy repository keeps test subjects outside its Nix dependency graph.

The roster contains enrolled identities only. Its initial coverage preserves existing enrollment of `nixos-cross-config` and `nixos-registry`; pending legacy records do not enroll projects. Audit all listed identities with `audit WORKSPACE --fetch --github`, retaining the JSON report. The audit discovers each release from the exact clean checkout, verifies its immutable publication and commit, invokes its checker with the captured central snapshot, and checks actual merge requirements. Missing callers, disabled enforcement, invalid selections, missing checkouts, or inaccessible metadata remain visible failures or inspection errors. See the [audit report contract](checker.md#enrollment-audits).

Retain a new identity in the legacy `projects` map before pin batches refer to it. A modern member can use an inert compatibility placeholder with `repository`, `adopted: false`, `policyVersion: null`, and `vmTargets: []`; these values do not track the member's selection or settings. Preserve all prior entries and all historical batch references when removing a member from the active roster. Completed and withdrawn batches still need their project names to resolve for supported older checkers.

Older selected releases retain their readiness and adoption process. Preserve `policyVersion`, `requiredArchitectures`, `vmTargets`, adoption state, and full `requiredChecks` as needed by those immutable consumers. Existing entries and historical batch references remain available when a member migrates; a new-contract caller does not require a central selection or activation update.

## Releases

`VERSION` contains the prepared policy version without the `v` prefix. The release tag adds that prefix, for example `0.1.0` becomes `v0.1.0`. A policy release includes shared rules, development requirements, checker code, and workflows. Shared pins and enrollment remain current operational records; their copies in a release do not establish current approval.

Prepare a release PR with `VERSION`, the changelog, and migration notes. Review compatibility of the rules, checker CLI and reports, workflow inputs, and record schemas. At 0.x, incompatible changes require a minor bump; compatible changes may use a patch bump. Preserve supported older consumers across the whole snapshot. Retire affected old releases explicitly and complete their migration before removing legacy data.

Human merge authorizes publication after the exact release commit passes checks on both Linux architectures. Establish `main` and its required merge gates before the first release. Enable [GitHub immutable releases](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/establish-provenance-and-integrity/prevent-release-changes) before publication. Prepare a draft release targeting the checked commit, include the reviewed changelog and migration notes, then publish it with the exact version tag. Verify that GitHub reports the release as immutable and that its tag resolves to the checked commit. Do not reuse a tag or publish from an unchecked branch head. Ordinary PR merges and the candidate-artifact workflow do not publish releases.

For v0.4.0 and later, a reviewed member PR changes policy links, the workflow reference, `policy_version`, and any settings required by the new contract. Central legacy selections remain unchanged. Verify newly generated statuses and actual merge gates when coverage changes. Keep older checkers and their record interface usable until explicit retirement and a migration period; publication of a newer release does not impose an automatic upgrade deadline.

## Retirement and legacy cleanup

Publishing a release leaves earlier selections supported. Retirement requires a separate reviewed central decision in `policy/support.json`, naming the affected exact release, the review reference, the reason, and an explicit migration start and effective retirement time. Announce the decision with enough time for the reviewed migration scope; the checker enforces a positive migration period but does not invent a universal duration. The initial record contains no retirements, and preparation of v0.4.0 retires no release.

Before the effective time, member checks and audits report the supported selection with its pending decision. At the deadline, new-contract local and CI commands fail the retired selection and central audits retain it as a failed enrolled member. Members migrate through their own reviewed PRs. Do not remove an entry from the roster to hide retirement failure, rewrite an immutable checker, or claim that its historical local command gained retirement enforcement.

Preserve all legacy records until affected releases are retired and their consumers have migrated. Retained adopted entries keep complete check lists even when their copied selections are stale. Completed and withdrawn pin batches retain their identities and references. Publication, an announced future deadline, absence from current selections, and roster removal do not establish cleanup safety.

For a separately reviewed cleanup proposal, run `nix run .# -- --policy-root PROPOSED validate --previous-policy-root TRUSTED_BASE --workspace MEMBERS`. Use the actual trusted prior central snapshot, not a reduced snapshot from the proposal. The command blocks cleanup for supported legacy releases, inspects published immutable patch releases, and verifies the union of prior/current enrolled identities at exact clean migrated commits using their selected checkers. It returns review evidence without removing data or authorizing a merge. Plain `validate` is only a structural check. Preserve the snapshot identities and migration evidence with the cleanup PR; maintain human review and compatible schemas. See the [support and cleanup contract](checker.md#release-support-and-retirement).

## Integration project agreement

Creating or enrolling an integration project remains a separate decision. An integration project keeps its behavioral checks in its root flake and adopts [the integration caller template](../templates/integration-caller.yml) after its selected release is published. Declare `Integration / Policy agreement` as an additional required check, keep the agreement caller on the same release as `Policy`, and retain its exact source/record output bindings. Run `ci PATH --project NAME` to inspect the full gate set and `agreement PATH --project NAME` from the selected checker against trusted records to inspect the committed dependency set. Verify the actual GitHub status and review merge-setting changes separately.

Upgrade the integration selection and the complete matching dependency set together when ready. Member current branches may upgrade independently while the integration lock retains older matching supported revisions. Review every reported lock scope, source revision, selection, and support decision. Preserve the ordinary committed-lock tests, both shared-pin compatibility checks on every required architecture, and applicable VM tests; policy agreement does not establish functional compatibility. Keep member dependencies acyclic and policy code outside member flake inputs and builds. See the [agreement command and evidence contract](checker.md#integration-policy-agreement).

## Migration to v0.4.0 (prepared)

This repository prepares v0.4.0; it does not publish the release, migrate members, change live gates, or approve pins. Publish the immutable release only through the separately authorized release procedure before activating callers. Select each member migration independently.

In one member PR, update the workflow reference, `policy_version`, and policy documentation links to `v0.4.0`. Copy the member's intended required architectures into the literal `required_architectures` input, encoded as JSON. Copy applicable VM targets and additional gates into `vm_targets` and `additional_required_checks`; omit these optional inputs when empty. Do not add a settings file or inputs for arbitrary records or compatibility pins.

Preserve existing required coverage unless a reviewed change explicitly justifies a reduction. Run `ci PATH --project NAME` and verify the expected names against actual PR statuses and GitHub merge gates. The mandatory status names are unchanged from v0.3.0 for equivalent settings; applicable VM gates remain on x86_64 even with ARM-only ordinary jobs. Additional names require member-owned jobs to produce them.

Keep the member's committed root nixpkgs selection and run both shared-pin compatibility channels on each declared architecture, the separate committed-lock check, formatting/lint, compliance/shell checks, and applicable VM suites. No central selection, settings, or adoption update is needed for this upgrade. Checks report enrollment separately and cannot authorize enrollment or pin approval.

Retain all legacy project entries and fields, complete required-check lists on adopted records, and identities referenced by historical pin batches. A migrated member's old central settings describe the retained legacy contract and need not track its new caller. Remove obsolete records only after explicit retirement of affected older releases and completed migrations. Neither an independent upgrade nor publication of v0.4.0 changes their support status.

## Migration to v0.3.0

Publish the immutable v0.3.0 release before activating member callers. Select each member migration separately, updating policy links, the workflow reference, `policy_version`, and `policyVersion` together. The mandatory workflow status names and matrices remain unchanged from v0.2.0. Project records retain schema version 2; no member migration, pin approval, merge-setting change, or release publication follows from preparing this release.

Move project-specific gates from the member's full `requiredChecks` list to `additionalRequiredChecks`, omitting the new field when there are none. Use `ci --project NAME` to derive the complete required set from the selected release, architectures, VM targets, and additional checks. Confirm that the observed statuses and GitHub merge gates match that set, preserving evidence on the migration PR.

Retain a full `requiredChecks` list for every adopted legacy entry until reviewed cleanup removes the obsolete entry. Older checkers require that field on all adopted records, even those selecting a newer release. For a migrated member, the retained list must exactly match the generated set. During preparation, keep `adopted: false` and omit the compatibility list if it needs regeneration. Cleanup requires explicit effective retirement and member migration; absence from current selections alone does not authorize it. Pending entries can omit their lists throughout preparation.

## Migration to v0.2.0

Publish the immutable v0.2.0 release before activating member callers. Keep existing members on their recorded 0.1.x releases until their individual migrations are selected and reviewed. The project and pin record schemas remain unchanged; the central audit invokes each older enrolled member's selected checker with the same record snapshot. This policy release does not enroll or migrate members, approve pins, change GitHub settings, or authorize publication.

For an explicitly selected member, retain its committed root lock, name the selected dependency `nixpkgs` regardless of update branch, and ensure both shared revisions support its actual root checks. Keep the normal shell/tool and committed-lock checks. No compatibility wrapper flake or second root input is needed solely to hold shared test pins. Existing extra inputs, examples, and transitive selections still need the applicable shared pins.

Update policy links, the reusable-workflow reference, `policy_version`, and the current `policyVersion` record together. Use the caller name `Policy`, record `requiredArchitectures`, and run `ci --project NAME` with trusted current records to obtain the complete mandatory gate set. Trial both compatibility channels on every recorded architecture and perform an end-to-end member run before activation. Inspect actual GitHub statuses on the reviewable member PR, including `Compatibility (stable, <architecture>)` and `Compatibility (unstable, <architecture>)` for each recorded architecture. Caller job prefixes are part of the exact names. Register only the observed names in `requiredChecks`, retain the ordinary policy and applicable VM gates, and obtain separate authorization before changing GitHub merge settings. A predicted name or passing policy-repository fixture does not establish a member gate.

Store the runner's metadata and results with the PR's CI evidence. Preserve the project, checker, and record commits and the record digest for replay as described in the [checker reference](checker.md#compatibility-execution-and-evidence). Retest all affected projects whenever either candidate revision changes, even when their default locks stay unchanged. Human approval remains required for pin approval, member activation, merges, and release publication.
